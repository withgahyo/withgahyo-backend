# AUTH API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the five AUTH APIs for Kakao login, Google login, logout, token refresh, and user withdrawal/reactivation.

**Architecture:** Add a focused `domain.auth` package for API, token, OAuth, and refresh-session use cases, while keeping `domain.user` responsible for user persistence and account state. JWT access/refresh tokens are signed with HMAC using environment-backed configuration, refresh tokens are stored server-side with rotation and revocation, and authenticated APIs read the current user from Spring Security.

**Tech Stack:** Java 21, Spring Boot 4.1.0, Spring Security, Spring Data JPA, Bean Validation, JUnit 5, Mockito, JDK `HttpClient`, JDK cryptography.

**Spec:** Notion API pages `API-AUTH-001` through `API-AUTH-005`, `docs/api-design.md`, `docs/erd-design.md`, and user-confirmed withdrawal/reactivation policy from 2026-08-19.

## Global Constraints

- Work on the current branch only.
- Commit each API as a separate feature commit.
- Do not include pre-existing `AGENTS.md` or `docs/api-design.md` changes in commits unless explicitly changed for this work.
- Do not hardcode OAuth secrets, JWT secrets, provider tokens, or personal data.
- Use `ApiResponse.success(data)` for data responses and `ApiResponse.ok()` for empty success responses.
- Use `SecurityErrorCode` for authentication and authorization failures.
- Store refresh tokens server-side and rotate them on reissue.
- Withdrawal soft-deletes `users.deleted_at`, revokes all user refresh sessions, keeps family rows, and reactivates the same row on later same-provider login.
